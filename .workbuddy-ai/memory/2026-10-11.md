# 2026-10-11

## 修复：bundled ThinkPHP 5 在 PHP 8.4 下无法运行（show_php_document 无弹窗）

问题：`show_php_document`（选中单词查看 PHP 函数说明）在 PHP 8.4 下报
`Return type of think\Container::offsetExists($key) should either be compatible with
ArrayAccess::offsetExists(mixed $offset): bool ...`，随后 `Class think\Container not found`，
弹窗不出现。根因是 tp5/ 内置的 ThinkPHP 5.1 + Medoo 1.6.1 是 PHP 5.6 时代代码，
其 `think\Error::appError` 会把**所有** PHP 诊断（含 E_DEPRECATED）抛成致命异常，
类声明期的弃用告警因此直接中断，导致类未声明。

修复（逐层暴露并解决，共 12 个文件）：
1. `#[\ReturnTypeWillChange]`（PHP<8 为注释，向后兼容）加到所有实现 ArrayAccess /
   Countable / IteratorAggregate / JsonSerializable 但缺返回类型的方法：
   Container(6)、Collection(7)、Paginator(7)、Config(4)、Model(4)、db/Where(4)、
   model/concern/Conversion(1)，共 33 处。
2. `Container::bindParams()`：`ReflectionParameter::getClass()`（8.0 起弃用）改用
   `getType()`（按 `PHP_VERSION_ID >= 80000` 分支，旧 PHP 行为不变）。
3. `think\Error::appError()`：E_DEPRECATED / E_USER_DEPRECATED 直接 return，
   不再抛异常（PHP 8.4 的“隐式 nullable 参数”等装饰性弃用遍布旧代码）。
4. `db/Query.php:568`：`$value{0}` → `$value[0]`（花括号字符串偏移 PHP 8.0 已移除，硬解析错误）。
5. Medoo 1.6.1 反序 `implode()` 共 10 处 + `db/Builder.php` 1 处：
   `implode($array, ',')` → `implode(',', $array)`（PHP 8.0 移除反序调用）。
6. `application/sublime/view/doc/find.html`：`{volist ... id="i"}` 未指定 key，
   TP5 volist 的计数器默认也叫 `i`，生成 `$mod = ($i % 2)`（$i 是数组）→ TypeError。
   补 `key="key"`，与同文件第一个 volist 一致。

验证：macOS + PHP 8.5.7 下 `php tp5/public/index.php
"sublime/index/run/call/app\sublime\command\FindCommentCmd/args/<base64>"` 返回
`{"code":200,"type":"show_popup",...}`；strlen / array_filter / preg_match / trim /
array_merge / preg_replace_callback 均 200，未知函数返回 404 error_dialog，lang=en 正常；
冷缓存可复现；tp5 全量 234 个 php 文件 `php -l` 通过。

注意（未改，属上游遗留）：`app\sublime\command\ListCmd` 在 PHP 8 下若传入字符串键参数会
报 “Unknown named parameter”，但 UI 无入口（`php_box` 从不以空 call 调用），实际不可达。

## 修复：php_box.py parse_php_result 错误路径连环崩溃

用户报：base64 解码失败时 `result_str` 未赋值 → `UnboundLocalError`。
写 harness（stub sublime / sublime_plugin，以包方式 import php_box）复现后发现同一错误路径
其实有 **3 个** 崩溃，只修用户报的那个仍会崩：

1. `UnboundLocalError`：`b64decode` 抛 `TypeError`/`binascii.Error` 时 `result_str` 未绑定。
2. `ValueError`：PHP 错误信息含非 ASCII（如中文）时，`b64decode(str)` 内部
   `_bytes_from_decode_data` 抛 `ValueError`，原来两个 except 都没覆盖。
3. `TypeError`：base64 合法但非 JSON 时，弹完错误框后 `result` 仍是 0，
   继续走到 `executeReceive(0)` → `'int' object is not subscriptable`。

修法（采纳用户提的“return after reporting”而非 `result_str = out.encode()`，
因为后者只是把崩溃下移一行）：b64decode 的 except 合并为
`(TypeError, ValueError, binascii.Error)`，报 `PHP ERROR:\n{out}` 后 `return`；
JSON 失败分支同样在报错后 `return`。顺带删掉因此变成死代码的 `result = 0;`。

验证：5 个单测分支全部正常返回并弹出对应错误框（原 3 个崩溃 + happy path 不变）；
端到端跑真实 php 命令喂给 parse_php_result，正常函数 → show_popup、未知函数 → error_dialog。

环境事实（排查用）：TP5 把异常渲染到 **stderr**，`os.popen` 只读 stdout，
所以纯框架报错时 `out` 为空（静默 return，不弹框）；用户遇到的非空 `out` 是
PHP CLI 自身把 fatal 打到 stdout 造成的。
另：`php_execute.run()` 拼命令时 URL 未加引号，Windows cmd.exe 保留反斜杠所以正常，
POSIX sh 会把 `\` 当转义吃掉 → 在 macOS/Linux 上 call 名会被破坏（未改，非本次范围）。

## 修复：php_box.py 拼命令未加引号（跨平台）

承接上一条的遗留项，用户要求“另开一处修”。`php_execute.run()` 原来是：

    self.php_bin + ' "' + command_bin + '" sublime/index/run/call/' + self.cmd + ...

`os.popen` 在 POSIX 走 `/bin/sh -c`，未加引号的 `app\sublime\command\FindCommentCmd`
反斜杠被 shell 当转义符吃掉 → call 名变成 `appsublimecommandFindCommentCmd` → PHP 返回
“没有...对应的方法或函数”。Windows 的 cmd.exe 不把 `\` 当转义符，所以只在 POSIX 暴露。

修法：三个参数各自加双引号（php 路径、index.php 路径、整个 URL）。
顺带覆盖 `php_path` 含空格的场景（如 `C:\Program Files\...`）。

验证（harness 直接调用真实 `php_execute.run()`，stub 掉 sublime）：
- 旧拼法 → PHP 返回 `没有appsublimecommandFindCommentCmd对应的方法或函数`
- 新拼法 → 正常返回 `show_popup` 及正确内容
`py_compile` 通过；parse_php_result 5 个分支与集成测试均无回归。

补丁拆分（三个独立补丁，均已 `git apply --check` 验证可干净应用到 HEAD，
且三个一起应用后与工作区逐字节一致）：
- `php8-compat.patch`            —— tp5/ 的 PHP 8.4 兼容（第一轮）
- `php-box-parse-error.patch`    —— parse_php_result 错误路径（第二轮）
- `php-box-command-quoting.patch`—— run() 命令加引号（本轮）

`check_php()` 里的 `os.popen(php_path + ' -v')` 同源问题也一并修了（用户要求“一并处理”），
归入 `php-box-command-quoting.patch`：加引号后 php 路径含空格（如 `C:\Program Files\...`）
不再被 shell 拆成多参数。

验证：造了 `/tmp/php with space/php` 软链到真实 php，调用真实 `check_php()`：
普通路径与含空格路径均返回 True 且不弹输入面板；旧写法在含空格路径下
`os.popen` 输出为空（sh 报 `/tmp/php: No such file or directory`）→ 会被误判为未配置 PHP。
parse / run / check_php 三个套件均无回归。

## 修复：php_path 默认值 / 输入面板不落盘 / 不自动重跑

用户报四个问题：
1. `PhpBox.sublime-settings` 硬编码 `E:/wamp64/bin/php/php7.2.12/php.exe`，与 README 第 58 行
   “命令行里 php 可用”（即走 PATH）矛盾。
2. 输入面板默认值硬编码 `/usr/local/bin/php`，在 Windows 上是错的。
3. 面板里输入的路径只 `settings.set` 没有 `sublime.save_settings`，重启即丢。
4. 填完路径后不重跑命令，用户得点两次。

修法：
- `PhpBox.sublime-settings`: `php_path` 默认改为 `"php"`（走 PATH，与 README 一致）。
- `check_php(path, on_ready=None)`：`php_path = path or 'php'`（未配置回退 PATH，
  顺带避免 `None + ' -v'` 的 TypeError）；`on_done` 里加 `sublime.save_settings`；
  保存后调用 `on_ready()` 回调；面板默认值改为当前 `php_path`（不再硬编码 POSIX 路径）。
- `PhpBoxCommand.run`：传 `rerun` 回调 —— `self.view.run_command('php_box',
  {'call': call, 'cmd_args': cmd_args})`，填完路径自动重跑，无需用户再点一次。

验证（stub sublime 的 harness，跑真实 `check_php` / `PhpBoxCommand.run`）：
- 合法路径 → True 不弹面板；`None` → 回退 PATH 成功；非法路径 → 弹面板且 initial 为当前配置值
- 模拟用户输入后：`save_settings` 被调用、值已写入、回调触发
- `PhpBoxCommand.run` 全链路：非法配置 → 弹面板 → 输入正确路径 → 保存 + 以相同
  call/cmd_args 重跑 `php_box`（不会无限递归，每次都需要用户输入）

## 建立 CI：push master 自动发版到 Package Control 频道

**关键事实**：本插件已收录在 Package Control **官方频道**，条目见
`sublimehq/package_control_channel` → `repository/p.json`：

    {"name":"PhpNinJaManual",
     "details":"https://github.com/yangweijie/SublimePHPNinJaManual",
     "labels":["php manual"],
     "releases":[{"sublime_text":">=3000","tags":true}]}

`"tags": true` ⇒ Package Control 直接读仓库的 git tag。所以「发布新版到频道」
== 构建通过后推一个版本 tag，**不需要**自建 channel.json/packages.json，也不用自己托管 zip。

新增（均未提交）：
- `.github/scripts/ci-check.sh` —— 本地/CI 共用：py_compile + tp5 全量 `php -l`
  + 冒烟测试（跑 `tp5/public/index.php`，断言返回 `code=200`）。
  注意冒烟 URL 必须整体加引号，否则 POSIX shell 吃掉反斜杠（同前面的 bug）。
- `.github/workflows/release.yml` —— `on: push: branches:[master]`：
  `build` job（setup-php 8.4 + pdo_sqlite/sqlite3/mbstring → ci-check.sh）
  → `release` job（`needs: build`；fetch-depth 0；推算下一个 patch 版本；打 tag 并 push；
  `gh release create`）。用 `git tag --points-at HEAD` 做幂等跳过；`concurrency` 串行化；
  `permissions: contents: write`。Release 说明 = `messages/<版本>.txt`（若有）+ 自上一个 tag 起的提交列表。

验证：ci-check.sh 本地跑通（233 个 php 文件，冒烟 code=200）；
负向测试 —— 塞一个语法错的 php → 脚本 exit 255；冒烟断言喂垃圾 → exit 1；
版本推算 1.0.3→1.0.4，无 tag 边界 0.0.0→0.0.1；
YAML 用 ruby 解析确认 build/release 结构与 `on.push.branches=[master]`。
